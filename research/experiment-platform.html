Experiment Platform

A sensor characterization rig. Cam drives a capacitive sensor, LCR meter measures it, force gauge verifies it. Two layers: interactive bench mode and autonomous optimization loop.
Author

Dan Vu

Published

June 14, 2026

We needed to characterize capacitive sensors under mechanical load. The question is simple: how does capacitance track applied force across different drive frequencies and probe configurations? Running this by hand means one person at the bench for hours, adjusting brackets, watching an oscilloscope, writing numbers in a notebook, and inevitably missing something. The experiment platform replaces all of that with a script.

Three instruments are involved. An LCR meter measures capacitance and parallel resistance over serial. A Vernier GoDirect force gauge measures force over USB at up to 1000 Hz. An Arduino Mega drives a cam against the sensor via PWM. The platform orchestrates all three, logs everything to CSV, and runs two experiment types: a static LCR frequency sweep and a dynamic actuator experiment where the cam oscillates at controlled frequencies while capacitance and force are recorded simultaneously.

Two layers, one threading core

The platform has two entry points that share the same concurrency model. cli.py is the interactive bench runner. It prompts for a box label and sensor index, offers LCR static, actuator sweep, or both, and loops over sensors with human-in-the-loop bracket selection and retry prompts. This is what a researcher uses at the bench.

run_headless.py is the autonomous optimization layer. It reuses the same ForceState, threading functions, and CSV writing from actuator.py, but strips out every interactive prompt. The loop decides its own next move by reading metrics from score_run.py, a frozen ruler that computes SNR, drift-corrected contrasts, and noise floor from the CSVs a run produces. The knobs it tunes are LCR probe frequency and aperture. The goal is maximizing signal-to-noise without a human in the loop.

Both layers share a single config.py file as the source of truth for all parameters: sweep frequencies, mechanical frequencies, bracket positions, servo gains, hardware ports, output directories. No hardcoded values anywhere else. A researcher edits one file. The loop edits the probe frequency and aperture fields. Everything else is read-only.

The threading model

The actuator experiment runs three concurrent flows and one shared mutable object. The shared object is ForceState, a lock-guarded cell holding the latest force reading and its timestamp. That is the only mutable state shared between threads.

The force thread steps the frequency controller at the GoDirect sensor rate, publishing force to ForceState on every sample. The LCR thread measures capacitance as fast as the meter allows, which is about 40 Hz — the hardware bound, not a code limit. Each LCR measurement grabs the latest force from ForceState under lock and pushes a complete row to a queue. The main thread drains the queue to CSV.

This design means force and capacitance are never perfectly synchronized. The LCR meter takes 25 to 40 milliseconds per measurement. By the time it returns, the force gauge has produced several new readings. The row written to CSV includes force_age_ms: the difference between the LCR timestamp and the force timestamp. This column is the whole sync diagnostic. If force_age_ms is large and variable within a run, the lock contention pattern is wrong or the LCR meter is unusually slow. If it is small and stable, the two sensors are effectively synchronized at the timescale that matters.

Stabilization before recording

Before recording begins at a target mechanical frequency, the force thread runs alone in a stabilization phase. The main thread polls FrequencyController.last_hz until it lands within the configured tolerance of the target, or times out. This is not a tight control loop. The controller updates last_hz every five seconds by counting force peaks. The stabilization loop accounts for this lag: it does not expect instantaneous convergence.

If stabilization times out, the frequency is skipped with a log message. Nothing crashes. The experiment moves to the next bracket or frequency. This is designed for unattended runs that might hit a loose bracket or a sensor that shifted during an earlier frequency step. The data from that step is lost, but the run continues.

Interleaved variant

The optimization loop uses a variant called interleaved mode. Instead of recording one LCR probe config per run, it walks a schedule of config blocks within a single continuous strike train. Each block switches the LCR probe frequency and aperture, tags every row with config_id and block_index, and runs for a fixed number of mechanical cycles rather than a fixed number of seconds. The force thread runs continuously across all blocks, so every config sees the same sensor state scattered across the drift direction.

The scorer then fits drift out as a nuisance covariate. Drift-corrected SNR lets the loop compare configs that were measured seconds apart on a sensor that might be warming up, settling, or degrading. Without this, the loop would mistake drift for a better probe setting and optimize toward whatever config happened to run last.

The quality heuristic

The LCR static sweep includes a sensor quality check called _is_clean. Six checks, empirically tuned for the specific capacitive sensor under test. Rejects negative capacitance, coefficient of variation above 0.20, monotonicity violations, outlier jumps, and end-point degradation below fifty percent of the initial value. If a sweep fails, the researcher is prompted to re-run or discard.

This heuristic is the kind of thing that sounds subjective until you watch someone spend twenty minutes analyzing data from a sensor that was dead before the experiment started. The check catches the obvious failures before they reach analysis. The thresholds are editable in one place. If a sensor type needs different criteria, change the numbers.

Safety and what it does not cover

The killswitch subsystem watches a flag file at the repo root. If a file named STOP appears, the headless runner zeros PWM on the live Arduino handle and aborts. A standalone command, killswitch.py stop, writes the flag and tries to open the Arduino port to force PWM zero directly.

Here is the gap. On Windows, COM ports are exclusive. If the runner holds ARDUINO_PORT, the standalone stop command cannot open it. The safety depends on the runner process being alive and scheduling threads to poll the flag file. A wedged process, a USB hang, or kill -9 bypasses the watcher entirely. The code is explicit about this. There is no firmware dead-man switch. Do not run the loop fully unattended.

A second runtime guard watches peak-to-trough force over a five-second sliding window. If the swing drops below a configurable threshold mid-run, the cam has stalled or the tape loosened, and the run aborts with a non-zero exit code. Running the optimization loop against a mechanically dead rig would produce garbage metrics, and the loop would tune toward whatever random noise the LCR meter picked up.

The import shim

All three roots — repo root, system_code/, optimization_project/ — are on sys.path via a venv .pth file. Every module imports flat: from config import ..., from killswitch import ..., no package-qualified imports like system_code.experiments.actuator. The .pth file is not checked in because .venv/ is gitignored. A fresh checkout must recreate it before anything runs.

This is ugly. The alternative is proper package layout with namespace packages and pip install -e ., but that would add setup overhead and break the existing import chains that the actuator platform upstream already depends on. The shim is a deliberate tradeoff: ugly but zero-friction for the workflows that exist.

What I would change

The two-layer split between system_code/ and optimization_project/ happened incrementally. The interactive platform came first. When I needed a headless loop, I added a new directory and imported threading functions from the interactive code by flattening the import paths. This works but it means the threading core lives inside actuator.py, which is also the interactive experiment runner. If I were starting over, the threading model would be its own module that both entry points import from, and actuator.py would be thin orchestration plus the interactive prompt loop.

The import shim would also go away. Proper package structure from the start would have saved the .pth hack and the mental overhead of explaining it in the architecture doc.

But both of those are about cleanliness, not correctness. The rig runs. The data is good. The optimization loop converges. The sync diagnostic (force_age_ms) proved that the threading model works at the timescale that matters. Everything after that is refactoring.
