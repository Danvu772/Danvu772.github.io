Single-file async app. BLE capacitance sensor to SQLite to REST API. Auto-reconnect, staleness detection, rolling buffer.
Author

Dan Vu

Published

June 14, 2026

We have a BLE capacitance sensor that broadcasts readings over the Nordic UART Service. I needed something to receive those readings, persist them, and expose them over a REST API so other lab tools could grab the latest value without knowing anything about Bluetooth. The whole thing is 434 lines of Python in one file.

It scans for a device matching a configurable name prefix, connects, subscribes to TX notifications, parses integer readings, writes them to SQLite with a rolling buffer cap, and serves a FastAPI on port 8000 with endpoints for health, status, latest reading, and history. If the device drops, it reconnects on its own after a configurable backoff. No external database, no message broker, no Docker. One process, one file.

Three async tasks, one queue

The app runs three concurrent tasks in a single asyncio event loop. The BLE receiver task scans, connects, and subscribes to notifications in an infinite loop with reconnect backoff. The DB writer task drains an asyncio.Queue and persists readings to SQLite. FastAPI runs on the same loop through uvicorn.

The handoff from BLE to database crosses a sync-to-async boundary. Bleak’s notification callback is synchronous and fires on a background thread owned by the OS Bluetooth stack. The callback parses the raw bytes into an integer and pushes it onto the async queue with loop.call_soon_threadsafe. That is the only threading concern in the whole app. asyncio.Queue is not thread-safe for put, and call_soon_threadsafe is the standard asyncio escape hatch for exactly this.

Any packet that will not parse as an integer gets logged as a warning to a file and dropped. The BLE connection stays open, the queue stays clean, and the API never sees a None reading.

SQLite with a rolling cap

The readings table has five columns: an auto-incrementing ID, the integer value, an ISO 8601 timestamp with milliseconds, the device name, and the device address. Every insert triggers a count check. If the table holds more rows than MAX_READINGS (default 5000), the oldest rows get deleted to bring it back to the cap.

The cap is a rolling window, not a time-based TTL. The history endpoint always holds exactly the most recent N readings, regardless of how fast the sensor transmits. At 10 Hz, 5000 readings is about eight minutes of history. At 1 Hz, it is over an hour. You lose older data silently, but for a lab tool that exists to answer “what is the sensor reading right now, and what was it doing for the last few minutes,” that is the right tradeoff.

The trim query deletes by ID rather than timestamp to dodge a full table scan on every insert. With a 5000-row cap, the delete touches at most a few rows per insert, even if the table briefly runs one over.

Staleness as a first-class concept

A reading can be stale for two reasons. The device disconnected and the BLE receiver has not reconnected yet. Or the device is still connected but has not transmitted within STALE_THRESHOLD_SECS seconds (default 5). Both get checked on every API request.

The /data/latest endpoint returns a stale boolean next to the reading. If stale is true, the value you are looking at might be seconds or minutes old, and you should not treat it as live. The /status endpoint reports connection state and staleness separately, so a monitoring dashboard can tell “device is gone” apart from “device is present but silent.”

This matters because capacitive sensors in our setup throw the occasional spurious BLE disconnect when the environment is noisy or the sensor gets moved. The auto-reconnect loop picks it back up within a few seconds, but during that gap any tool polling the API needs to know the data is not current. A stale flag is simpler and more honest than handing back a null and making the consumer guess why.

The reconnect loop

The BLE receiver task is an infinite loop with three phases: scan, connect, wait for disconnect. Scan finds no matching device, it sleeps for RECONNECT_BACKOFF seconds and tries again. Connection fails, same thing. Connection succeeds and the device later drops, the disconnected_callback sets an asyncio.Event the task is awaiting, wakes it, and it goes back to scanning.

No exponential backoff, no max retry count, no circuit breaker. The device is a lab sensor on a bench three feet away. If it is not connecting, the problem is physical: dead battery, out of range, powered off. Exponential backoff fixes none of those. A fixed five-second retry means the researcher sees a five-second gap, fixes the hardware, and the app picks it up on the next scan.

Configuration without a config file

All configuration is environment variables with defaults, loaded from a .env file by python-dotenv. Device name prefix, database path, log path, buffer size, staleness threshold, scan timeout, reconnect backoff, API host and port. Every constant reads from os.getenv with a fallback.

This is deliberate. A JSON or YAML config adds a parsing step and a file-format dependency for six strings and integers. Environment variables are the config format every deployment tool already speaks. The .env file gives you file-based config for development, the environment gives you deploy-time config for everything else, and the code does not change between the two.

The API surface

Four endpoints. GET /health returns {"status": "ok", "version": "0.1.0"}. GET /status returns connection state, staleness, device info, last seen timestamp, and uptime. GET /data/latest returns the most recent reading and a stale flag. GET /data/history?n=100 returns the last N readings, newest first, with optional device name and address filters.

The history endpoint caps n at MAX_READINGS so a request for 1000000 rows cannot scan the whole database. The SQL uses a parameterized LIMIT, not a string format, so the query planner treats it as a bound parameter.

Every endpoint returns a Pydantic model declared on the route decorator. FastAPI uses these for OpenAPI schema generation and response validation. The models set from_attributes = True, so they can be built from ORM-style objects. The database rows are not ORM objects, they are plain tuples from aiosqlite, but the model constructor is called by hand with keyword arguments. So the flag is future-proofing rather than something the code leans on today.

Lifespan management

FastAPI’s lifespan context manager handles startup and shutdown. On startup it initializes the SQLite database, creates the table if it is missing, and spawns the DB writer and BLE receiver as asyncio tasks. On shutdown it cancels both tasks, awaits their cancellation, and closes the database connection.

This beats global __init__ side effects or module-level asyncio.create_task calls you cannot await on shutdown. The lifespan is the one entry and exit point for every async resource. If the app crashes, the exception propagates through the lifespan and uvicorn restarts the process. The database connection always closes, either by await db.close() on the shutdown path or by the process exiting.

What I would change

The BLE callback parses bytes to int and enqueues in the same function. If the parsing ever gets more involved (signed values, multi-byte packing, different formats per device), that callback would need to split into parse and enqueue steps with the parse step testable on its own. Right now parsing is one call to int() and the only failure is a ValueError, which is caught and logged. For a single sensor emitting plain integer strings, fine. For several sensor types, not fine.

The staleness check compares last_seen against datetime.now(timezone.utc) on every API call, and last_seen updates in the DB writer after a successful insert. If the callback fires but the DB write runs unusually long (which should not happen for a single-row insert into a local SQLite file), the API could call a reading stale while the writer is mid-insert. A separate last_received timestamp set in the BLE callback, independent of the DB write, would close that gap.

I would also add a WebSocket endpoint. Polling /data/latest from a dashboard is fine for a few clients, but a live capacitance trace wants push. The pieces are already there: the async queue is a natural fan-out point and FastAPI has first-class WebSocket support. It was out of scope for v0.1, which targeted a single consumer running a data logging script.
