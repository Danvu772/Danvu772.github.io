Syringe Pump Automation

hardware
automation

Multi-pump syringe control for Harvard and New Era pumps. Rate limits validated before serial, worker thread per pump, tkinter UI plus script-based orchestration.
Author

Dan Vu

Published

June 14, 2026

We run experiments that need three syringe pumps moving at once: one Harvard Apparatus Pump 11 Elite and two New Era NE-4002X pumps daisy-chained on a single RS-232 line. The Harvard speaks one serial protocol. The New Eras speak another, with address prefixes for the daisy chain. Neither has a Python driver that validates rates properly. Both will happily accept an out-of-range command and either reject it at the firmware level with a useless error code or, worse, run at some rate you did not ask for.

This software wraps both pump types behind one PumpController API, with hardware-level rate and volume validation that runs before any serial command reaches the pump. It ships a tkinter UI with three tabs (setup, manual control, script orchestration) and a run.bat launcher that makes the whole thing double-clickable on Windows.

Rate limits as a feature, not a guardrail

The key decision is that rate validation is not a safety net. It is the primary interface. Every infuse and withdraw call checks the requested rate against the pump’s mechanical limits at the given syringe diameter before it builds the serial command. Out of range, it raises RateOutOfRange with the exact allowed range in the message. The command never reaches the port.

This matters because the two pump types have wildly different limits at the same diameter. Take a typical 12 mm syringe. The Harvard can push up to 18.3 mL per minute. The New Era NE-4002X, a microfluidic pump, tops out at 0.249 mL per minute at the same diameter, about seventy times slower. Write a protocol that assumes both pumps handle 1 mL per minute and the Harvard is fine while the New Era rejects it. Validation catches that before the experiment starts, not thirty seconds into a dispense when one pump has already moved.

The limits are diameter-dependent because flow rate is pusher velocity times syringe cross-sectional area. The Harvard’s pusher travels from 0.000153 to 159.0 millimeters per minute. The New Era’s limits come from a per-diameter table in the spec sheet, interpolated between listed values and clamped to an absolute ceiling of 1226 microliters per minute. Every number in pump_limits.py is back-solved from the manufacturer documentation and checked against hardware. The docstrings cite the source document and appendix.

Volume caps

The Harvard has no hard ceiling on a single dispense. The New Era firmware uses a four-digit microliter field, which caps a single dispense at 9999 microliters, roughly 10 mL. Ask for more and it raises VolumeOutOfRange. The workaround is continuous mode (set volume to zero and time the run yourself) or a loop of smaller dispenses. The error message says which. It does not just refuse and leave you guessing.

Per-pump worker threads

Each registered pump gets its own PumpWorker thread with a task queue. Setup commands (diameter, rate, volume) are queued as callables and run sequentially in the worker. The main thread stays responsive, which matters in the UI, where a frozen window looks exactly like a crashed program.

The workers are plain threading.Thread instances with daemon set to False. They run until a sentinel None task arrives or a stop event is set. Errors collect in a per-worker list rather than raising in the calling thread, so a setup failure on pump B does not stop pump C from initializing. The UI polls the error lists and surfaces failures per pump.

The daisy-chained New Eras share one serial port. The NewEraNetwork class owns the port and each NewEraPump holds a reference to it plus an address. A lock on the network keeps two pumps from talking over each other on the shared bus. The Harvard gets its own COM port and never contends for anything.

The UI

Three tabs. Setup configures and connects each pump one at a time: type, port, address, and a Connect button that turns green when the pump answers. Manual runs one or more pumps right now with fixed settings: diameter, rate, volume, direction, Run. Orchestrate is a text editor with a Run Script button.

Orchestrate is where it gets interesting. Paste a Python script straight into the editor, or hit Load to open one from protocols/, or Insert Template for a skeleton, or LLM Prompt to copy the full API context to your clipboard so you can drop it into any model and have it write the protocol for you. The generated script goes back in the editor. Run Script releases the UI’s COM port connections, spawns the script as a subprocess, streams its stdout into the log pane, and reconnects the pumps when it finishes.

The STOP ALL button at the bottom kills any running subprocess, reconnects the pumps, and sends a stop to every registered pump. It is the emergency brake, so you never have to find the terminal window, dig up a PID, and kill it by hand.

The script API

Scripts use the same PumpController as the UI, so there is no second interface to learn. A script opens its own controller and COM ports, runs the experiment, and closes everything in a finally block. The template includes a Ctrl+C handler that calls stop_all and close_all before exiting, so an interrupted script leaves the pumps stopped instead of free-running.

from pump_controller import PumpController

ctrl = PumpController(log_file='logs/experiment.log')
ctrl.add_harvard('pump_a', port='COM6')
ctrl.add_new_era('pump_b', port='COM7', address=0)

ctrl.run_parallel([
    {'pump_id': 'pump_a', 'rate': 1.0, 'units': 'ml/min',
     'volume': 2.0, 'diameter_mm': 14.43, 'direction': 'infuse'},
    {'pump_id': 'pump_b', 'rate': 0.2, 'units': 'ml/hr',
     'volume': 0.5, 'diameter_mm': 8.58, 'direction': 'withdraw'},
])
ctrl.close_all()

run_parallel blocks until every pump in the list finishes. infuse and withdraw on a single pump block too. That is intentional. The API is synchronous because async pump control adds complexity without buying anything for this use case. Need two pumps moving together? Use run_parallel. Need them in sequence? Call infuse then withdraw on separate lines. There is no event loop to reason about.

LLM integration as a deliberate side channel

The LLM Prompt button does not call an API. It opens a popup with a text block: the full hardware configuration, the syringe diameter reference table, the rate limit tables, the API reference, and the generation rules. You copy it, paste it into ChatGPT or Claude, and describe your experiment in plain English. The model writes a complete script with the right diameters, rate limits, and error handling. You paste the result back into the editor.

This is deliberately low-tech. Embedding an LLM call would add an API key, a network round trip, and a failure mode I cannot reproduce. Copy-paste keeps the model as a tool the researcher uses, not a dependency the software carries. If the model is down, you still have the template and the API reference. If the model writes bad code, you read it before you run it. There is no black box between you and the motor.

The prompt text lives in llms.txt at the project root, so it doubles as documentation for any human who wants the full API surface in one file.

What I got wrong

The original protocol assumed both pump types could handle milliliter-per-minute rates. Wrong by a factor of forty for the New Era at a typical diameter. I found out when the hardware rejected a rate and handed back a firmware error code with no explanation. The fix was pump_limits.py, which back-solves every limit from the manufacturer docs and checks the table entries against real hardware responses. That table is now the single source of truth for what any pump can do at any diameter.

Then there was the volume convention. PumpController takes milliliters, the New Era firmware speaks microliters, and the driver converts internally. I did not document that clearly at first, so a script asked for 0.001 mL thinking it meant 1 microliter and got exactly that. Correct, and confusing, because the log showed a number that did not match the mental model. The convention is now stated in every code example and in llms.txt.

I would also redo the worker thread model. As it stands, tasks queue per pump and there is no way to wait for all setup across all pumps to finish before starting. The UI papers over this with status polling, but a script that calls add_harvard and then infuse immediately can race the setup. A wait_until_ready that blocks until every worker has drained its queue would close the gap.
