I kept rewriting the same peak-extraction code across calibration experiments. Find the max, subtract a baseline, pull some slopes off the shape. Every notebook had its own version, each broken in its own special way. The third time I tracked down a sign error in a width calculation, I gave up and made it a library.

dpv-monopeak does one thing. You hand it a voltage array and a current array from a Differential Pulse Voltammetry scan with a single dominant Faradaic peak. It hands back eight electrochemical features and every intermediate it used to get them. That is the whole scope.

The monopeak assumption

The name is the constraint. One Faradaic peak per scan, no more. If your voltammogram has multiple redox couples, the global current maximum wins and everything else is treated as background. No peak fitting, no deconvolution.

That looks like a limitation. It is the point. Multi-peak DPV is a different problem with different failure modes and a baseline model that is far more involved. Refusing to handle it keeps this library small enough to read in one sitting and fast enough to run on thousands of scans without anyone wondering what is happening inside.

The baseline and the capacitive hump

DPV scans from our instrument carry a characteristic artifact. On the left side of the peak, before the Faradaic current rises, there is a hump: a slow climb in baseline current as the electrode double layer charges and discharges. Search naively for the current minimum left of the peak to anchor your baseline and you latch onto the tip of that hump instead of the real pre-peak floor. The baseline tilts up, the corrected peak height shrinks, and everything downstream comes out wrong.

The fix is the left-chop heuristic. The entire thing:

def _find_left_chop(i, peak_idx):
    quarter_end = peak_idx // 2
    if quarter_end == 0:
        return 0
    return int(np.argmax(i[:quarter_end]))

Three lines. Take the quarter of the scan before the peak. The current maximum in that window is the shoulder of the capacitive hump, so start the left-anchor search there and exclude everything before it.

This is embarrassingly simple and it works, because the hump always sits in the first half of the pre-peak region for the scans this instrument produces. Different instrument, different artifact shape? Inject your own left_chop_fn and the rest of the extraction logic does not change. The interface is (i: ndarray, peak_idx: int) -> int. Return an index. Done.

The eight features

Once the anchors are placed, the rest is deterministic geometry. The baseline is a straight line between the left and right current minima flanking the peak. The corrected current is i - baseline. From there:

X is the peak voltage, the voltage at the maximum of the corrected current. This is your redox potential proxy, the primary signal of which analyte you are looking at.

Height is the peak current after baseline subtraction. It scales with concentration and it is the most direct quantitative feature.

Area is the trapezoidal integral of the corrected peak between the anchors. It holds up better than Height when the peak shape shifts across replicates.

Width is the FWHM, the voltage span at half the peak height. It needs both half-max crossings to exist and returns NaN if one is missing, which is more honest than guessing.

YOffset is the baseline current at the peak voltage, the non-Faradaic background. If this drifts across a concentration series while Height stays flat, your electrode is fouling rather than the analyte changing.

MaxSlope and MinSlope are the steepest rising and falling slopes of the corrected peak, computed as finite differences on the raw data with no smoothing. Positive and negative by convention. Sharp peaks get large absolute values, broad peaks get small ones.

SumSlope is MaxSlope + abs(MinSlope), a single number for peak sharpness. Narrow, well-defined peaks score high. Broad, flat peaks score low.

Every one of these has a physical meaning. None of them are dimensionless scores or model embeddings. They are numbers you can point at on the voltammogram and explain to a colleague in one sentence.

When it returns None

The extraction returns None when the scan does not contain a valid single peak. Arrays of different lengths, fewer than five points, flat current, duplicate voltage values, a peak sitting at either edge of the window, a positive peak height (which would put the baseline above the peak, impossible for a real Faradaic signal), zero peak area. Each gets its own early return with no diagnostic message.

That is deliberate. The calling code loops over hundreds of scan files. When a scan fails, the loop skips it and logs the filename. A detailed error per scan would bury the researcher in noise. The failure is the signal: this scan has no valid monopeak, move on.

Two functions, not one class

Two public functions, no classes. extract_dpv_features returns the eight features as a flat dict. compute_dpv returns those eight plus every intermediate: the baseline array, the corrected current, the half-max indices, the derivative array, the slope indices. Use extract_dpv_features for batch processing and compute_dpv when you need to plot a result or debug a scan that is misbehaving.

They share internals. extract_dpv_features calls compute_dpv and drops the extra keys. No duplication, and no way for the two paths to drift apart.

from dpv_monopeak import extract_dpv_features

v = df["v_V"].to_numpy(dtype=float)
i = df["i_uA"].to_numpy(dtype=float)
feats = extract_dpv_features(v, i)
if feats:
    print(f"{feats['X']:.4f} V, {feats['Height']:.2f} uA")

Plot as sanity check

The optional plot_dpv function gives you a two-panel figure: raw current with baseline on top, corrected current with FWHM and area shading on the bottom. It takes the same left_chop_fn parameter, so the plot matches whatever extraction logic you are running. It is the fastest way to confirm the baseline is reasonable on one scan before you batch-process three hundred.

Plotting is optional because matplotlib is heavy and this library is pure numpy by default. pip install dpv-monopeak[plot] pulls it in. The core stays at one dependency.

Testing against synthetic peaks

The test suite generates Gaussian peaks on flat and tilted baselines and checks the extracted features against analytic ground truth, to within discretization error. Peak voltage within one sample step, height within one percent, FWHM within two sample steps, area within five percent. Off-center peaks, edge peaks, linear baselines. The left-chop heuristic is tested for correctness and for pluggability: inject a recording lambda and confirm it was called exactly once with the right peak index.

Every edge case that returns None has a test. Peak at the last sample, flat current, mismatched array lengths. If a scan should fail, the test asserts it does.

dpv-calibration

There is a sibling package, dpv-calibration, that turns these eight features into concentration-response curves. Point it at a directory of scans from known concentrations, it extracts features from each, fits a model, and returns calibration parameters. It is less mature, currently in that awkward phase where the API surface is mapped out but the edge cases are still being found by throwing real data at it. It exists because once feature extraction is clean, calibration is the obvious next thing, and bundling both into one package felt wrong. Feature extraction is a solved problem here. Calibration is a modeling problem with its own failure modes.

What I got wrong

The monopeak assumption is baked into the package name and every function signature. Right call for the instrument it was built for. It also means that if someone hands you a scan with two Faradaic peaks, the library quietly picks the taller one and pretends the other is not there. A validate_monopeak check that scans the corrected current for secondary peaks above some fraction of the main Height would catch it. I skipped it because every scan I had seen from our instrument was single-peak. The first time I ran it on a different dataset, that assumption broke.

The other miss is error reporting. Returning None from every failure path is clean code and terrible debugging. When a batch job runs 200 scans and 14 silently drop, you have no idea why until you re-run those 14 through compute_dpv and stare at the intermediates. A reason key next to the None would have saved me an afternoon.
